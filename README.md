# 多环境隔离：K8s命名空间与资源配额，从“分开了”到“真的隔住了”

做K8s多环境隔离最容易踩的坑，是把“创建了命名空间”当成“完成了隔离”。开发、测试、生产三个Namespace建好，资源各自部署，看起来干干净净。但真实故障往往来自一个被忽略的事实：**命名空间默认只隔离名字，不隔离行为**。一个开发环境的Pod默认可以访问生产环境的数据库，一个测试环境的批处理任务默认可以吃光整个节点的CPU，而生产环境对此毫无感知。多环境隔离的设计，核心不是画几个逻辑分区，而是回答一个问题：**当某个环境出问题时，它的爆炸半径能控制在多大**。

**第一件事：先选隔离模型，再谈配额数字**

多环境隔离有三种模型，选错模型的代价远大于配错一个数值。命名空间级隔离是成本最低的起点，适合同一信任域内的内部团队和环境划分，依赖RBAC、NetworkPolicy、ResourceQuota三层配置共同兜底。但它的隔离是“软”的：Pod共享节点内核，一个内核漏洞或一个没有配NetworkPolicy的命名空间，就能让隔离形同虚设。如果开发环境跑的是不可信代码，或者合规要求明确禁止跨环境共享内核，命名空间就不够，需要节点池隔离甚至独立集群。GKE的推荐路径很务实：从命名空间开始控制成本，只在合规要求升级时提高隔离强度。这个判断的教学含义是：**隔离强度应该由“最坏情况下谁受影响”决定，而不是由“哪个方案最省事”决定**。

**第二件事：ResourceQuota和LimitRange必须成对出现，缺一个都会漏**

只配ResourceQuota不配LimitRange，会出现一个Pod占满命名空间大半配额的情况：一个没写limits的容器，可能把整个团队的内存额度吃光，其他服务无法创建。只配LimitRange不配ResourceQuota，命名空间整体仍然可以被大量小Pod拖垮。两者的分工是：ResourceQuota管命名空间的总量上限（CPU、内存、Pod数、PVC数），LimitRange管单个容器的默认值和上下限（没写requests时补默认值，超出max时拒绝准入）。

一个容易被忽略的联动规则是：**当命名空间存在ResourceQuota时，该空间内所有Pod必须显式声明requests和limits，否则准入被拒绝**。这意味着LimitRange的default和defaultRequest不是“建议值”，而是让工作负载能通过配额准入的必需配置。学生在设计配额方案时，应该先确认LimitRange的默认值已经就位，再配ResourceQuota，顺序反了会导致上线时一片Pod创建失败。

**第三件事：配额数字应该按环境意图给，而不是按“统一标准”给**

给所有命名空间配同样的配额，是教学场景里最常见、生产环境里最危险的做法。一个轻量Web API的requests可能只有100m CPU，一个批处理任务需要2 CPU，一个ML训练Pod可能需要8 CPU以上。统一配额的结果是：轻量团队浪费额度，重负载团队撞墙后要求特批，平台团队陷入无休止的调额请求。

更务实的做法是按环境意图分层：开发环境给低配额、快速反馈，测试环境给中等配额以运行接近生产规模的验证，生产环境给较高配额但配更严格的监控和告警。LimitRange的默认值也有一个可参照的起点：轻量服务的默认request可以设在100m CPU/128Mi内存，默认limit在500m/512Mi，limit与request的倍数关系CPU可以放宽到3到5倍，内存建议控制在2到3倍以降低OOM风险。这些数字不是圣旨，但“先给保守默认值、观察2到4周实际用量再迭代”的方法论比任何具体数字都重要。

**最后一条实用建议：配额超限时的排错顺序，决定了恢复速度**

Pod创建被拒绝时，第一反应不应该是“调大配额”。正确的排查顺序是：先看报错原文区分是Quota超限还是LimitRange校验失败；再查配额使用详情确认是CPU、内存还是Pod数先到顶；然后查实际占用区分是真实业务增长还是僵尸Pod和未清理的测试资源；最后确认LimitRange的单体上限是否卡住了合理扩容。这个顺序的训练价值在于：**大部分“配额不够”的问题，实际原因是资源没清理或默认值不合理，而不是配额本身设小了**。先清理再扩容，比直接加数字更接近根因。多环境隔离的终点不是“三个环境互不干扰”，而是“任何一个环境的异常行为，都不会让其他环境替它买单”。
